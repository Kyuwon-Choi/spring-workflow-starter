# 기존 로직을 유지하며 요구 변경하기

변경마다 `변경 ID | 이전 규칙/출처 | 새 규칙/출처 | 적용 대상·시행 기준 | 유지할 조건 | 영향 코드·데이터 | 검증`을 남긴다. 새 요구로 원래 계약을 지우지 않는다. 담당자의 답이 없는 중요한 업무 정책은 질문으로 남긴다.

## 먼저 확인할 질문

- “새 기준은 생성/제출/승인 중 어느 시각부터 적용하나요? 시간대는요?”
- “이미 제출/승인/반려된 건과 반려 재제출은 각각 어느 규칙을 쓰나요?”
- “역할 이동·프로젝트 제외·위임 취소가 기존 화면과 처리 중 요청에 어떻게 적용돼야 하나요?”
- “새 조건이 기존 필수 조건을 대체하나요, 특정 경우만 추가하나요?”
- “한 건 금액 제한인가요, 여러 요청이 공유하는 잔여 예산인가요?”

## 구현된 규칙 버전 예

정책 예시: V1은 부서 승인으로 완료, V2는 **300000 초과**만 재무 승인, 새 규칙은 제출 시 선택하고 재제출은 새 제출로 취급한다.

| 상황 | 기대 동작 |
|---|---|
| V1 제출 뒤 V2 게시 | 기존 건은 V1을 유지 |
| V2 게시 뒤 300000 제출 | 부서 승인으로 완료 |
| V2 게시 뒤 300001 제출 | 부서 승인 뒤 FINANCE_PENDING |
| 같은 사람이 부서·재무 역할 보유 | 두 단계 승인자가 같으면 거부 |
| V1 건 반려 뒤 V2로 재제출 | V2 선택, 이전 이력 보존 |
| 위임 취소/프로젝트 제외 | 이후 요청부터 현재 권한으로 거부 |

이 예는 실제 EnterpriseScenarioTest와 HTTP/화면으로 확인한 패턴이다. 다른 과제에 정책을 그대로 적용하지 말고 담당자 합의를 받는다. 기존 규칙 버전을 유지하는 것과 취소된 접근 권한을 유지하는 것은 다르다.

## 변경 순서

1. 기존 정상 동작과 유지할 계약을 기대 사례로 고정한다.
2. 새 요구가 현재 실패하는 입력/상태/계정/시각을 정한다.
3. 정의 변경인지, 계산 확장인지, 정책 변경인지, DB migration인지 나눈다.
4. 영향을 받는 조회/단건/동작/검색 건수/집계/CSV/이력/연결 객체까지 확인한다.
5. 공유 예산 등 여러 객체를 바꾸면 단일 객체 version만으로 충분한지 검토한다.
6. 변경하고 관련 기존/신규 검증을 실행한다. 필요한 경우 전체 검사를 한 번 수행한다.
7. 실제 결과·미검증·새 실행 방법을 WORK와 README에 반영한다.

현재 조직 예제는 회사 잠금→객체 잠금 순서로 변경을 직렬화한다. 예산·요청·이력은 같은 트랜잭션이며 실패하면 함께 되돌린다. 외부 알림/결제는 이 DB 롤백으로 취소되지 않는다. 외부 연동은 별도 재시도·중복 방지·실패 복구가 필요하다.

## 데이터 변경 경계

필드 타입·필수값·상태 이름을 바꾸면 기존 payload가 새 정의와 맞지 않을 수 있다. 기존 changeSet을 수정하지 말고 새 migration과 변환/호환 계획을 정한다. 기존 일반 업무에 조직 정책을 추가할 때 과거 행의 회사/부서/프로젝트를 추측하지 않는다. 테스트 DB만 성공했다고 기존 파일 DB 업그레이드까지 성공으로 기록하지 않는다.
