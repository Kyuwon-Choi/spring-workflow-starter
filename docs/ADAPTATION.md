# 새 업무에 적용하는 실습

처음에는 [빠른 시작](QUICKSTART.md)으로 기본 앱을 실행한다. 실습은 기존 기본 예제를 없애지 않고 새 도메인 하나를 추가한다. 제공 저장소 수정 과제에서는 전체 앱을 교체하지 말고 필요한 패턴만 적용한다.

## 1. 요구를 정의로 바꾸기

연습 업무: 요청번호·제목·예상비용으로 업무 요청을 만들고, 작성자가 제출하며 관리자가 완료 또는 사유를 남겨 반려한다. 이 예제는 **단순 역할 승인**이다. 관리자 자기 승인 금지·회사 격리가 필요하면 [조직 정책](ENTERPRISE-GUIDE.md)을 연결해야 한다.

완전한 정의 예제는 [service-request.json](examples/service-request.json)이다. 실행 중인 서버를 종료한 뒤 파일을 복사한다.

```bash
cp docs/examples/service-request.json src/main/resources/fde/domains/service-request.json
./scripts/dev.sh
```

새 정의는 서버 시작 때 읽힌다. JAR를 쓰면 [재빌드 순서](QUICKSTART.md)를 따른다. label만 바꾸는 것으로 새 업무 정책을 충족했다고 판단하지 않는다.

## 2. 실제로 확인할 흐름

1. user로 `/fde`에서 “업무 요청 실습”→“요청”을 고른다.
2. 요청번호 `REQ-001`, 제목 `자료 검토 요청`, 예상비용 `10000`을 입력해 생성한다. 상태 DRAFT, 서버 owner/version이 표시되어야 한다.
3. 직원 “제출”→PENDING. 같은 직원에게 관리자 완료/반려 동작은 없어야 한다.
4. 로그아웃 후 admin으로 같은 건 조회→“완료”→DONE. 생성/제출/완료의 이력을 확인한다.
5. user로 `REQ-001`을 다시 만들면 고유 키 충돌이 나야 한다. 다른 번호는 생성되어야 한다.
6. 두 번째 요청을 제출하고 admin으로 사유를 넣어 반려한다. 직원이 반려 사유를 읽고 재제출하면 PENDING이 되어야 한다.

이 정의의 `decisionNote`는 생성 입력을 막는 readOnly 필드다. 직원에게 감추는 필드가 아니며 재제출 시 기존 사유를 지우지 않는다. 사유 초기화/비공개 정책이 요구라면 그 요구를 확정하고 확장과 검증을 추가한다. 위 흐름은 사용자가 수행할 실습의 기대값이며, JSON 등록 검사와 구분한다.

## 3. 어떤 파일을 바꿀지

| 요구 | 첫 선택 | 확인 |
|---|---|---|
| 필드·enum·상태·라벨·반려 입력 | 정의 JSON | [계약](DOMAIN-REFERENCE.md), 타입/필수/경계값 |
| 다른 객체 참조 | procurement/support 정의 참고 | 같은 도메인 타입의 실제 ID, 대상 접근 권한 |
| 수량·상한·할인 계산 | FdeExtension | StockAdjustment, 음수·경계·원자성 |
| 회사/부서/프로젝트·민감 필드 | FdePolicy | 조회 SQL·단건·출력·CSV·검색까지 |
| 금액별 다음 승인 단계 | EnterpriseCommands 패턴 | 제출 버전·경계·서로 다른 승인자 |
| 전체 입력 이력 분석·파일 정답 | 분석 recipe | 기대 집계/오류 파일, 웹앱 필요 여부 |
| 외부 알림·결제·연동 | 별도 실패/재시도 경계 | DB 롤백만으로 외부 처리가 취소되지 않음 |

## 4. 확장 연결

계산은 Spring bean으로 등록한 FdeExtension의 고유 id를 Action.extension에 연결한다. `changes(current,input)`은 바꿀 업무 필드 맵을 반환한다. 고급 `apply`는 changes와 선언된 상태 중 다음 상태를 반환한다. 반환 값은 공통 엔진에서 다시 타입 검사하고 객체/이력을 같은 트랜잭션에 저장한다.

`current`/`input`에는 임의의 사용자 주체를 추가하지 않는다. actor는 서버 인증 컨텍스트에서 구한다. `FdePolicy`가 있는 타입은 SQL scope·생성 메타데이터·업무 키·검색 색인·단건 동작·출력 필드를 함께 설계한다. `visibleFields(type,null)`은 CSV 열 후보에도 사용되므로 null을 처리해야 한다.

같은 계약의 새 조직 도메인은 정의로 재사용할 수 있다. 필드/동작/상태가 다르면 enterprise id만 붙이지 말고 어댑터를 구현한다. [요구 변경](CHANGE-CONTROL.md)에서 데이터 호환을 확인한다.

## 5. 실습을 작업 결과로 남기기

WORK에 요구→정의/확장→완료 조건→실제 결과를 기록한다. 실습 전용 파일은 자신의 작업 브랜치에서 관리하고 필요 없으면 추가한 파일만 제거한다. 기존 예제/이전 DB를 일괄 삭제하지 않는다. 새 도메인 등록·권한·경계 테스트를 추가한 뒤 관련 검사부터 수행한다. 이번 저장소의 전체 기준은 [검증 기록](VALIDATION.md)을 본다.
