# 범용 업무 키트 사용 가이드

2026-10-28. 이 구현은 동일한 업무 처리 경계를 여러 도메인에 적용하는 코드 키트이며 Palantir Foundry의 동등 구현은 아니다.

## 두 가지 준비물

1. **업무 처리 제품:** 입력·스키마·관계·목록·폼·액션·권한·집계·이력·결과를 제공하는 공통 엔진과 화면.
2. **특수 문제의 출발점:** [GitHub 선택 카드](REPO-CATALOG.md). 분석·문서·최적화·그래프 등은 해당 검증/참고 경로를 선택한다.

‘어떤 도메인도 80%’는 원 후기의 준비 목표다. 실제 과제의 필수 요구를 모르므로 달성률로 표시하지 않는다. 이번 증거는 공통 기능을 바꾸지 않고 업무 정의와 확장 함수만 바꾼 범위다.

## 구조

```text
README/자료 → 담당자 질문 → 업무 정의
                           ↓
CSV/API → 타입·관계 검증 → 객체 저장 → 목록·폼·검색·집계
                           ↓
                      허용된 액션
                           ↓
             역할·범위·버전·선행 조건 검사
                           ↓
              상태/속성 변경 + 이력 같은 트랜잭션
                           ↓
                     조회·CSV 결과

업무 고유 계산 → FdeExtension → 동일한 검증/저장/이력 경계
```

## 공통 기능과 정의할 부분

| 공통 처리 | 도메인에서 정의/구현 |
|---|---|
| 필드 타입·필수값·범위 검사 | string/integer/decimal/boolean/date/enum/reference, 실제 조건 |
| 객체·참조 대상 검증 | types와 reference 대상 타입 |
| 고유 업무 키 중복 검사 | type.keyField, 실제 중복 기준 |
| 조회·검색·상태 필터·페이지·건수 | 상태 이름, labelField, readRoles/readScope |
| 서버 생성자·version·시각 관리 | 업무 payload에 임의로 system 값 대입 불가 |
| 폼·상세·목록·동작 입력 UI | 필드 label/type/options, action.inputs |
| 허용 동작·역할·범위·선행값 검사 | actions.from/target/roles/scope/requires |
| 입력을 속성에 적용 | actions.writes: 속성명 → 입력명 |
| 고유 계산 | actions.extension에 등록된 Java FdeExtension |
| 같은 DB 변경·이력·실패 롤백 | 무엇을 바꿀지 정의하고 민감 필드는 실제 요구에서 검토 |
| CSV 미리보기·일괄 입력·내보내기 | 열·타입·필수값·업무 키, 실제 데이터 |

기본 읽기 scope는 ALL과 OWN(생성자)이며 managerRoles가 OWN 범위를 확장한다. 담당자·부서·회사와 같은 뜻은 아니다. 회사/부서/프로젝트별 SQL 범위·출력 정책은 선택형 FdePolicy와 [조직 어댑터](ENTERPRISE-GUIDE.md)를 사용한다. 사용자 정의 정책은 조회·출력·검색·키 범위와 관련 검증을 함께 추가한다.

2026-10-28 가상 과제 검증으로 두 경계를 추가했다. 필드의 `readOnly: true`는 생성 API/CSV에서 입력을 거부하고 생성 폼에서도 제외한다. 선택 필드에만 쓰며, 신뢰된 액션 writes/확장 계산은 이 값을 기록할 수 있다. 역할별 열람 차단 기능은 아니다. 액션의 `scope: OWNER_ONLY`는 관리자도 타인 객체의 동작을 대신 하지 못하게 한다. 기존 OWN의 관리자 예외와 ALL 의미는 유지한다. 읽기 범위의 지원 값은 여전히 ALL/OWN이다.

## 실제 적용 증거

| 업무 정의 | 객체/관계 | 동작/정책 | 도메인별 코드 |
|---|---|---|---|
| support.json | 고객 → 문의 | 본인 문의 답변/종료, 관리자는 범위 확장 | 정의 JSON 1개 |
| procurement.json | 공급사 → 구매 요청 | 본인 제출, 관리자 승인/반려, 반려 사유 | 정의 JSON 1개 |
| inventory.json | 재고 품목 | 전체 조회/조정, 음수 재고 거절 | 정의 JSON + StockAdjustment 구현 |
| 테스트 전용 events.json | 행사·인원·날짜 | PLANNED → PUBLISHED | 테스트 리소스 JSON 1개 |
| 테스트 전용 training.json | 교육 → 지원 신청 | 본인만 제출·관리자 승인/반려·80%/30만원 상한 계산 | 테스트 정의 + TrainingGrant + 공통 필드/동작 경계 보완 |

이 네 경우 모두 FdeService/API/저장 테이블/공통 UI를 공유한다. 네 번째 정의는 테스트 classpath에만 추가해 엔진의 특정 예제 하드코딩 여부를 확인한다. 기본 소속 없는 계정에는 세 업무를 노출하며, enterprise 정의는 업무 소속이 있는 계정에서 추가 발견할 수 있다. 이 증거는 사람의 실제 도메인 적용 시간이나 모든 요구의 80% 충족을 뜻하지 않는다.

위 문단의 네 경우는 최초 검증 범위다. 이후 training은 다섯 번째 적용 사례로 추가했으며, 이 경우는 공통 코드 무수정 사례로 세지 않는다. 원본 앱에는 이 시나리오 정의와 계산을 테스트에만 넣었다. enterprise는 선택형 조직 정책/동작 확장을 추가한 후속 사례이며 [검증 기록](VALIDATION.md)에 범위를 구분했다.

## 새로운 업무를 붙이는 순서

1. 입력 자료·기존 저장소·제출 형식과 제약을 읽는다. 기존 프로젝트가 있으면 전체 앱 교체보다 필요한 패턴만 적용한다.
2. 담당자에게 사용자·구체 사례·성공 조건·예외·권한·출력 형식을 질문한다. 사실·답변·가정을 구분한다.
3. 객체/필드/관계/역할·데이터 범위/상태·동작 표를 만든다. 각 요구마다 완료 조건과 검증 입력·예상값을 정한다.
4. 가장 가까운 JSON을 복사해 새로운 id·types·fields·states·actions로 바꾼다. 도메인명만 바꾸고 정책을 그대로 유지하지 않는다.
5. 계산·할당·외부 연동이 필요하면 검증한 레포/모듈을 선택하고 작은 확장 함수를 붙인다. 단순 계산은 FdeExtension, 네트워크 부작용은 별도 실패·재시도 설계를 한다.
6. 재기동해 정의 검증을 통과시키고 입력 → 객체 → 관계 → 액션 → 결과 한 경로를 실제로 수행한다.
7. 잘못된 타입·관계·다른 계정·금지 동작·오래된 version·입력 중간 실패를 검증한다.
8. 출처·재사용 범위·변경 이유·실행 근거·한계를 문서에 남기고 직접 설명한다.

## 업무 정의 예

공통 JSON 형태를 이해하기 위한 축약이다. 실제 정의는 resources/fde/domains를 참조한다. 각 타입에는 읽기/생성 역할, 읽기 범위, 관리 역할, 모든 상태와 초기 상태를 명시한다. 임의 외부 JSON을 신뢰해 등록하지 않는다.

```json
{
  "actions": {
    "reject": {
      "label": "반려",
      "from": ["PENDING"],
      "target": "REJECTED",
      "roles": ["ROLE_ADMIN"],
      "scope": "ALL",
      "inputs": {"reason": {"label": "사유", "type": "string", "required": true}},
      "writes": {"reason": "reason"},
      "requires": []
    }
  }
}
```

## 구현 AI에게 연결할 카드

```text
프로젝트 경로: [실제 경로]
과제/데이터 경로: [실제 경로]
남은 시간·구현 종료 목표: [값]
허용 도구·자료: [확인한 규칙]

README와 docs/FDE-GUIDE.md, 실제 도메인 정의, FdeService,
FdeExtension, FdeWorkbenchTest, workbench.tsx를 확인해라.

확정 요구 [ID·출처]를 객체·관계·동작·권한·검증 표로 매핑해라.
기존 정의에서 바꿀 정책, 재사용하는 기능, 필요한 특수 모듈을 구분해라.
첫 흐름을 완성할 최소 변경과 검사 입력·예상값을 정해라.
공통 엔진을 바꿔야 한다면 정의/확장으로 해결되지 않는 이유를 먼저 설명해라.
실제 실행·실패·미검증을 구분하고 원래 테스트를 무조건 삭제하지 마라.
```

## 분석 과제로 전환

웹 업무 상태 변경보다 파일 집계·정답 계산이 핵심이면 불필요한 인증·DB·화면을 먼저 만들지 않는다. `recipes/analytics`에 검증한 DuckDB 입력/집계/출력 경로가 있다. 실제 열 이름과 계산 기준을 확인한 뒤 group/measure와 요구 계산을 바꾼다. 대시보드가 필요하면 Streamlit 카드를 검토한다.

## 지원하지 않는 것을 확인

선택형 조직/필드 권한·기간 위임·다단계 승인·규칙 버전·공유 예산은 [ENTERPRISE-GUIDE](ENTERPRISE-GUIDE.md)의 범위에서 구현/검증했다. 임의 깊이 조직 트리·다중 회사 동시 소속·복잡한 다대다 관계·장기 비동기 작업·외부 시스템 동기화·OCR·최적화·실제 AI 호출은 추가 구현 대상이다. HTTP 요청에 임의 SQL·스크립트를 받거나 외부 AI가 직접 권한·상태 검사를 우회하도록 하지 않는다. 기능 없는 버튼이나 샘플 응답으로 실제 연동을 대체해 완료 처리하지 않는다.
