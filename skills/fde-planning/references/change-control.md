# 기존 로직에 추가 요구가 들어왔을 때

변경 요청 또는 조직/위임/다단계 승인 정책이 등장했을 때만 읽는다. 기존 과제의 확인된 계약과 데이터를 먼저 살핀다.

## 요구 변경 기록

`변경 ID | 이전 규칙/출처 | 새 규칙/출처 | 적용 대상·시행 기준 | 유지할 조건 | 영향받는 요구/코드/데이터 | 확인 질문`

새 규칙을 문서 전체에 덮어써서 과거 결정과 요구가 사라지게 하지 않는다. 기존 필수 조건을 없애는 변경인지, 특정 조건에만 예외를 추가하는 것인지 확인한다. 총 요구 수와 충족 상태도 갱신한다.

## 계획 전에 결정해야 할 것

- 생성/제출/승인 중 적용 기준 시각, 시간대와 경계. 기존 진행/승인/반려/재제출 건의 소급·호환 정책.
- 관리자 예외, 자기 승인 금지, 부서/프로젝트/위임 범위, 위임 취소/만료와 실행 시점의 권한.
- 한 건의 제한인지 공유 예산/쿼터인지, 관련 상태와 외부 부작용의 원자성/재시도.
- 기존 API·응답·내보내기 계약과 데이터 migration의 필요성.

담당자 답이 없는 큰 정책은 확인 질문으로 남기고 영향받는 작업만 대기한다. 과거 계산 규칙을 보존한다는 이유로 취소된 접근 권한도 보존하지 않는다.

## 변경 실행 계획

기존 동작을 설명하는 사례와 새로운 요구의 실패 사례를 먼저 고정한다. 일반 입력 형식뿐 아니라 사용자×소속×대상×동작×상태×시각의 필요한 조합에서 허용/거부를 정한다.

권한은 화면 버튼·단건 API뿐 아니라 목록 SQL/페이지/총건수/집계/CSV/이력/연결 객체 출력까지 검토한다. 목록 전체를 가져와 UI에서 가리는 것으로 격리를 완료하지 않는다. readOnly 필드가 역할별 비공개 필드라는 뜻은 아니며 OWNER_ONLY가 자기 승인 금지라는 뜻도 아니다.

공유 예산·다른 객체를 추가로 갱신하면 단일 객체 version/락만으로 충분하다고 가정하지 않는다. 해당 업무의 트랜잭션·공유 행 락/원자적 조건 갱신과 동시성 검증을 계획한다. 외부 네트워크 부작용은 DB 트랜잭션과 별도 실패·재시도 경계다.

정책 선택·검증·계산·상태 전이를 구분하고 최소한의 확장 지점을 정한다. 실제 필요 없이 범용 규칙 언어·외부 정책 서버를 도입하지 않는다. 관련 새/기존 회귀 검증을 실행한 뒤 근거와 남은 미검증을 기록한다. 구현/실행 요청이 없으면 이 변경 계획을 작성하는 데서 범위를 지킨다.
