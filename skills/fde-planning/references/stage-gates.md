# 단계와 전환 조건

계획과 진행 재정렬에 사용한다. 아래는 개인 작업 운영 기준이며 공식 평가 절차나 채점 항목이 아니다. WORK 하나에서 현재 단계와 실제 근거를 관리한다. 요구별 검증 상태와 전체 작업 단계를 섞지 않는다.

| STATE | 이 단계에서 확보할 것 | 다음 단계 판단 근거 |
|---|---|---|
| DISCOVERY · 발굴 | 실제 사례·현재 처리·핵심 문제·자료와 미확인 | 핵심 흐름/정답을 바꾸는 질문과 영향이 드러남 |
| AGREEMENT · 서면 합의 | 문제·성공 기준·범위/제외·제약에 대한 확인 요청 | 실제 답변과 확인 범위. 미응답은 대기, 독립 준비는 병행 |
| SCAFFOLD · 기반 준비 | 제공 코드 우선, 실제 런타임/입력과 최소 변경 위치 | 기존 실행 또는 최소 입력 처리 성공, 환경 실패/전환 비용 기록 |
| E2E_V0 · 첫 흐름 | 실제 입력→규칙/계산→저장 또는 출력 | 독립 기대값과 실제 결과 일치. UI/mock만으로 완료하지 않음 |
| MID_CHECK · 중간 확인 | 담당자에게 보여줄 입력·결과·현재 한계·확인 질문 | 실제 답변에 따른 유지/수정 범위. 자체 검증과 담당자 확인을 구분 |
| ACCEPTANCE · 수용 확인 | 남은 필수 요구와 관련 정상/경계/권한·실패 검증 | 완료 조건별 증거, 담당자 수용 답변 또는 확인 대기/확인 불가 명시 |
| SUBMISSION · 제출 | 실행/파일·제출 형식·남은 한계·설명용 기록 | 실제 제출 ID/시각/확인 화면 등. 후보 준비와 제출 완료 구분 |

실제 산출물에 맞춰 기반 준비를 파일 처리 환경 확인처럼 작게 잡을 수 있다. 이미 확인한 근거는 재사용한다. 되돌아갈 때는 변경된 요구 ID와 이유만 남긴다. 답변이 없을 때는 현재 단계와 대기 중 확인을 함께 적고 확정된 독립 범위를 진행하며, 정답·권한·비가역 동작의 미확인 정책을 채우지 않는다. 마지막까지 담당자 확인을 못 받았다면 미확인으로 제출하되 수용 완료라고 쓰지 않는다.

단계 전환이나 중대한 요구 변경 때 다음을 짧게 확인한다.

1. 합의한 문제와 필수 요구에서 벗어난 변경이 있는가?
2. 통과·확인·제출 완료 표시마다 실제 실행/답변 근거가 있는가? 순조롭게 보여도 실패 사례나 반례를 한 번도 확인하지 않았는가?
3. 실제 남은 시간으로 필수 검증·수정·제출까지 가능한가?

매 단계마다 전체 문서·전체 테스트를 반복하지 않는다. Git이 허용된 경우 의미 있는 실행 지점에서 로컬 커밋을 남길 수 있지만 자동 공개 push는 하지 않는다.

## 중간 확인과 최종 수용

중간 확인은 `실제 입력 / 관찰한 결과 / 아직 안 되는 것 / 확인받을 판단`을 짧게 묶어 응시자가 담당자에게 보낸다. “괜찮나요?”보다 “이 사례에서 [결과]가 맞는지, [예외]는 어떻게 처리할지”를 묻는다. 성공 답변을 대신 만들지 않는다. 범위가 바뀌면 영향받는 요구·예상값·시간을 갱신한다.

최종 수용은 요구별 실제 검사와 담당자의 업무 적합성 확인을 구분한다. 숫자 개선 효과는 실제 측정한 경우만 주장한다. 인수 후 사용자/유지 담당자에게 필요한 실행 명령·입력 계약·핵심 파일·설정 위치·남은 한계를 남긴다. 설명은 질문 이유→선택 이유→데이터 흐름→검증→한계 순으로 응시자가 직접 할 수 있어야 한다.
